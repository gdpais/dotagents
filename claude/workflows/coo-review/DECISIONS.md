| COO-01 | Skill name | `coo-review` (unchanged); `portfolio-review`; `operations-review`; `coo-portfolio-review` | `coo-portfolio-review` | Keeps the user's "COO" term so existing phrasing still triggers it; "portfolio" states the scope. Kebab-case, no collision with any `engineering:*` skill, no "claude"/"anthropic". | codex:coo-review |
| COO-02 | Skill structure | Split into separate skills (review, lock, Linear sync); one skill with references | One skill, SKILL.md plus 5 references (4 ported and a new `claude-runtime.md`) | The steps share one lock, one run ID and one write owner, so splitting them would create hand-offs between parts that must not be separated. SKILL.md (about 130 lines) contains the whole core procedure, so it still works if saved on its own. References add depth when needed. | codex:coo-review / new |
| COO-03 | `agents/openai.yaml` | Ship as-is; drop entirely; fold into SKILL.md | Folded, file not shipped | display_name and short_description went into the description. The Linear MCP dependency became a "Requirements" line. `allow_implicit_invocation: true` became trigger phrases in the description (COO review, portfolio/operations review, project-state refresh, cross-project priorities). Claude has no default-prompt slot, so default_prompt was dropped, but its wording seeded the description. | codex:coo-review |
| COO-04 | Scheduling and Claude scheduled tasks | Allow an optional scheduled run; stay silent about scheduling; explicitly forbid it | Explicitly forbidden. Never create or modify scheduled tasks, cron jobs or delayed self-reminders. If a scheduled task started the session, stop before taking the lock. A request to schedule is treated as a change to the skill, which needs the user's permission for that change | Source: "Run only on demand. Do not create or modify a schedule" and "do not run on a schedule". Claude can create scheduled tasks, so the ban has to be explicit. An unattended run also breaks the design: nobody is there to answer the decision panel, recover a lock or grant folder access. No scheduled task was created in this port. | codex:coo-review |
| COO-05 | Where the COO workspace lives | Connected folder or local dir; claude.ai Project docs; Artifact database; Claude memory; cloud container | Connected folder (Cowork) or local directory (Claude Code). Ephemeral-only sessions run read-only and say nothing was persisted | Only a real filesystem gives an atomic create-exclusive lock and durable, user-owned files. Project docs and the Artifact DB have no create-exclusive primitive. Memory is for facts about the user, not portfolio state. Containers are ephemeral. | codex:coo-review / new |
| COO-06 | How the lock is implemented | Bundled lock script; inline shell commands; the file tool's write-if-absent | Inline POSIX shell: plain `mkdir` (never `-p`), `owner.json` via `printf`, token from `/dev/urandom`, one shell for the whole run. Tested locally | In Cowork the device shell cannot see the skill's own files, so a bundled script would have to be staged every run. Each device-shell call is a fresh process, so the token and run ID are carried explicitly. `mkdir` is the source's primitive. | codex:coo-review / new |
| COO-07 | Releasing the lock when deletion is blocked (Cowork forbids deletes in connected folders by default) | Request a delete grant; leave the lock held; atomic rename out of the lock path; recursive delete | Try `rm owner.json` then `rmdir`. If either fails, verify the token and rename the directory into `.released-locks/<run>-<ts>` | A delete grant covers the whole connected folder, which is more than the lock needs. A same-folder rename frees the lock path atomically without deleting anything. Recursive delete stays forbidden, as in the source. The fallback is noted in diagnostics, and `.released-locks/` is excluded from Git. | new (preserves codex rule) |
| COO-08 | Run ID and owner metadata | Allocate after reading state; allocate under the lock | Allocate `YYYY-MM-DD-NN` right after `mkdir` succeeds, reserve it with a stub review file, then write `owner.json` (token, run, session id or "unknown", host as the shell reports it, UTC time) | The source requires the lock before allocating IDs and the run ID inside `owner.json`. The stub means a run that fails early still leaves a dated review to record the failure. The session ID is never invented, and in Cowork the host is the workspace VM, which the runtime reference notes. | codex:coo-review / new |
| COO-09 | Recovering a stale lock | Recover by age; never recover; recover on verified termination or explicit user direction | The source rule, plus: ask the user (a genuinely blocking question). Recovery renames the old lock to `recovered-*` and is logged | Age alone is not proof, and a missing owner file is not permission (source). Claude cannot reliably check whether another session has stopped, so the user's explicit direction is the practical path. | codex:coo-review |
| COO-10 | Persisting ownership of Linear status updates | Only in the review; only in STATE.json; both | Update IDs go in the review's Linear section. STATE.json gets a new `runs` block with the update ID and a fingerprint of the content this run last wrote | The source needs "last content this run wrote" to decide whether an edit is allowed but gave no schema. Storing a fingerprint follows the "metadata only" rule. If STATE.json is lost, ownership is uncertain, and the source rule is then "do not edit". | codex:coo-review / new |
| COO-11 | Codex workers | Codex sub-agents; Agent tool subagents; everything in the coordinator | Agent tool subagents: at most 2 initially, only for substantial, independent, changed projects. A full brief template is provided. The return contract is kept word for word. If a subagent cannot reach the folder, the inspection runs locally | Direct mapping. The brief spells out what each subagent receives (one project, prior state, detected changes, evidence locations, drift lens) and must return. | codex:coo-review |
| COO-12 | Subagent access to Linear | Allow reads; forbid reads and writes | Subagents report the identifiers they come across but do not look anything up in Linear, and never write | This slightly tightens the source, which only forbade writes. With one reader/writer, the coordinator's baseline and pre-write re-read stay consistent and duplicate connector traffic is avoided. | codex:coo-review (tightened) |
| COO-13 | Linear tool mapping | Hardcode MCP tool names; CONNECTORS.md `~~project tracker` generalization; Linear connector described by capability | Linear connector described by capability, with a required-capability list. No connector or mapping means a "blocked change plan" (record, field, last observed value and date, intended value). No substitute tracker | The authorization is scoped to Linear only, so generalizing to any tracker would widen what the user authorized. Tool names differ between connectors. The fallback follows the source rule "do not represent unverified local assumptions as applied". | codex:coo-review / anthropic:CONNECTORS.md (rejected) |
| COO-14 | Authorization boundary | Keep "Apple Reminders or other external systems" as written; generalize | Linear only. Explicitly excludes reminders, calendars, scheduled tasks, chat, email and other trackers. Personal follow-ups are listed only | "Apple Reminders" was a Codex-environment detail. Claude has several native side-effect channels, notably scheduled tasks, so they are named explicitly. The intent is kept. | codex:coo-review |
| COO-15 | Private calendar data | Allow it if a calendar connector is attached | Never access it, even if attached. Use only deadlines and constraints the user supplies or authorizes | Kept word for word from the source. It is made explicit because Cowork users often have calendar connectors attached. | codex:coo-review |
| COO-16 | Decision-panel interaction | Plain chat question; AskUserQuestion for everything; AskUserQuestion for final consequential choices only | AskUserQuestion only for the final consequential D-NNN choices: after persisting state and releasing the lock, one question per ID, real alternatives only, defer only if genuine, recommendation labeled but not preselected. Unclear free text leaves the decision proposed | Follows the brief and the source rules (release the lock before waiting, don't invent alternatives, silence or interest is not acceptance). Routine Linear changes are never confirmed through it. | codex:coo-review / new |
| COO-17 | Reuse `engineering:standup` | Delegate per-project activity summaries to it; borrow its yesterday/today/blockers format; borrow its "tell me what you did" mode; not reused | Not reused (not delegated, nothing adopted) | Standup summarizes one person's recent activity from connectors for a daily ritual. User-supplied notes are already covered by the source's "reported constraints" class. Standup also encourages a daily habit ("Run it every morning"), which conflicts with on-demand only. | anthropic:standup (rejected) |
| COO-18 | Reuse `engineering:tech-debt` | Delegate debt audits to workers; adopt its scoring formula; adopt its six categories; not reused | Six categories adopted as an optional drift-lens checklist for deep inspections, gated by the user's materiality test.
